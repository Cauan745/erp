# Device regression checklist

Use this checklist after changes affecting products, inventory, checkout, recovery, or native dependencies. The current verification baseline is in the [README](../README.md#verification-status).

Start the API and Metro using the [development instructions](../README.md#development), then open the installed native app. VisionCamera requires that build. Keep all existing data and reminders; use clearly named test products and ordinary API actions. Never uninstall, clear storage, reset database volumes, or dismiss unresolved reminders merely to proceed with testing.

For each regression pass, record passed, failed, or not exercised for the affected rows. Check keyboard scrolling, safe areas, navigation/back, typed translations, and BRL/date formatting throughout.

| # | Device action | Expected result |
| --- | --- | --- |
| 1 | Create a product with stock 10, edit metadata, restart the app and API, and scan its barcode. Also check a zero or negative opening balance. | Products reload from the server with the right prices/stock. Metadata never changes stock. Opening balances create no history rows. Duplicate names differing only in ASCII case and exact duplicate barcodes show a translated conflict and retain the form. |
| 2 | Apply +2 and -3 to the stock-10 product. Edit, clear, and reopen a reason. Hide the product after recording a sale, then edit its adjustment reason again. | Stock is 9 before that sale, with exactly two adjustment rows. Reason edits preserve stock, quantity, timestamp, and request identity. Hiding removes the catalog/barcode result, retains history and reservations, and permits reason edits. Sale rows have no reason editor. |
| 3 | Scan known and unknown barcodes, hold a barcode in view, then disconnect during lookup. Close and reopen the scanner while a lookup is pending. Edit cart quantities. | One scan adds once. Only a genuine missing barcode offers registration. Connection failure has a retry action and retains the cart/catalog. Old callbacks cannot change a newly opened scanner. Cart quantities and estimates behave as before. |
| 4 | Make separate cash, debit card, credit card, and Pix sales. Try insufficient cash, exact cash, extra cash, repeated confirm taps, and Android back while saving. | Cash must cover the total and shows correct change. Noncash saves null cash/change. Each confirmed sale appears once and decrements stock once. Pending input and dismissal are guarded. Details retain quantities, names, prices, line totals, and payment after product edits/hiding and app/API restart. |
| 5 | Build a cart, then change its price through another API client before confirming. | The first attempt saves no sale/stock change. The cart shows revised prices, preserves payment/cash input, and requires another explicit confirmation. |
| 6 | Reduce stock through another API client after preparing a cart. Exercise cancel, replenish, and sell anyway, including multiple shortages. | Cancel preserves the cart. Overrides require explicit approval per product and earlier approvals accumulate. Replenishment is a separately saved adjustment and remains if checkout fails or is cancelled. Reopen its reason and save the unchanged translated value; the server retains `sale-shortage-replenishment`. |
| 7 | Start with the API unavailable, then restore it. Load all lists, disconnect and refresh each one. Background the app, change server data, and return with an unfinished form/cart/payment. | Navigation and reminders stay usable. Lists have independent errors/retries and retain old rows. Foreground refresh updates server data without losing input. Repeated refresh taps do not overlap reads for a list. Failed saves retain form/payment input. No offline business write appears later. |
| 8 | Interrupt a refresh immediately after a confirmed product save, adjustment, reason edit, or sale. | The write still reports success. Refresh failure is separate and retains the confirmed result/old rows. Retrying a list never resubmits a mutation. |
| 9 | For both an adjustment and a checkout, submit once and interrupt the response so the outcome is uncertain. Record the reminder/request ID, reopen the app before looking it up, then restore access and choose "Verificar solicitação anterior". | The marker survives app restart. No payload/cart is restored after a full process restart. Lookup confirms the original resource with one business effect and clears only that marker. In the original session, checkout input remains locked while uncertain. API logs show one POST and subsequent GETs, with no automatic replay or replacement request ID. A connection failure alone does not prove a response was lost after commit; record which case occurred. |
| 10 | Exercise a lookup while the original POST is still executing or before its commit is visible, using controlled delay/network tooling if available. Repeat lookup after completion. | `404 request_not_found` leaves the reminder unresolved, blocks replacement submissions, and never triggers a POST. A later 200 resolves the same request. The PostgreSQL tests prove server visibility and app doubles prove client handling; if real device timing cannot be reproduced, record this row as not exercised. |
| 11 | With an unresolved reminder, point Metro at another backend and reload. Check the reminder, then restore the normal backend. If several reminders already exist, verify each remains. | The lookup uses its recorded backend. Its result does not enter the other backend's lists or clear an unrelated form/cart. Every outstanding marker survives reload. Dismissing one reminder requires explicit reconciliation against its recorded server and warns that dismissal cannot cancel a running request. Do not reconcile merely to remove a test blocker. |
| 12 | Check keyboard scrolling, safe areas, navigation/back, category suggestions, camera permission text, Portuguese labels and BRL/date presentation throughout these flows. Background and reopen/restart the app once more. | Existing screens remain usable. English dictionary/fallback completeness is type-checked; exercise English if a test build/context exposes it. No background business request occurs. For native dependency changes, inspect the installed artifact after the lifecycle pass. |

For uncertain-request tests, use disposable test transactions and inspect the recorded server's history. Do not repeatedly tap submit to manufacture a duplicate. The UI offers lookup/reconciliation for uncertain input. If timing tools are unavailable, record the gap instead of treating a failure before submission as a lost committed response.

Record a failed flow's request ID and backend without clearing its reminder. Confirming a saved write followed by a failed refresh must never prompt another mutation. Automated recovery tests use storage/fetch/native doubles; actual storage persistence and network timing require device observations.
