### Adjustment mappings, queries, DTOs, and transaction

[`StockAdjustment`](../backend/src/main/java/com/stockroom/erp/stock/StockAdjustment.java) retains the V1 mapping: a server-generated UUID, lazy product foreign key, signed nonzero integer quantity, nullable reason, UTC creation time, unique request UUID, and immutable original fingerprint. Creation now truncates its timestamp to microseconds so the first response and later PostgreSQL lookups return the same timestamp. The initial integration run exposed nanosecond rounding differences; the corrected run passes. No schema migration was required. Opening stock still writes only the product row.

[`StockAdjustmentRepository`](../backend/src/main/java/com/stockroom/erp/stock/StockAdjustmentRepository.java) supplies ordinary JPA persistence and the derived `findByRequestId` lookup. [`StockTransactions.adjust`](../backend/src/main/java/com/stockroom/erp/stock/StockTransactions.java) checks request identity, acquires `ProductRepository.findByIdForUpdate`, then checks identity again before inspecting deletion state or current stock. Matching duplicates return the committed resource, including later reason edits. Different original fingerprints return `request_id_reused`. New adjustments reject missing/hidden products. `Product.adjustStock` uses checked integer addition and updates the managed balance and updatedAt. `saveAndFlush` inserts the adjustment and flushes the managed product in one READ COMMITTED transaction with a 20-second bound. Overflow returns `422 numeric_overflow`; rollback leaves both tables unchanged. PostgreSQL lock waits remain bounded at five seconds and translate to `503 inventory_busy`.

[`StockService.adjust`](../backend/src/main/java/com/stockroom/erp/stock/StockService.java) normalizes reason and computes the original fingerprint before calling the separate transaction bean. It catches only `stock_adjustments_request_id_unique` outside that failed transaction. The losing transaction has already rolled back before `StockTransactions.winner` reads and compares the committed winner in a fresh transaction. This covers races using the same request ID against different product rows, where product locks alone cannot serialize identity. No service interfaces, generic repository wrappers, or operation table were added.

[`CreateAdjustmentRequest`](../backend/src/main/java/com/stockroom/erp/stock/CreateAdjustmentRequest.java) requires a request UUID and integer quantity. Zero is rejected; omitted reason is allowed and explicit null is forbidden on creation. Existing strict Jackson settings reject fractions, numeric strings, duplicate fields, and unknown fields. [`AdjustmentResponse.from`](../backend/src/main/java/com/stockroom/erp/stock/AdjustmentResponse.java) reads the lazy product's ID inside the service transaction. Responses expose only the contract fields, never entities or fingerprints. [`StockController`](../backend/src/main/java/com/stockroom/erp/stock/StockController.java) returns 201 after the first committed mutation and 200 for matching duplicates. Request-ID GET is read-only and returns `404 request_not_found` for a lookup miss. A second application startup test retrieves the committed adjustment and stock through the new services.

### Reason edits and combined history

[`UpdateReasonRequest`](../backend/src/main/java/com/stockroom/erp/stock/UpdateReasonRequest.java) distinguishes an omitted reason from explicit null. `StockTransactions.updateReason` normalizes the value and calls the existing focused JPQL `updateReason`. That query changes only `StockAdjustment.reason`, checks the affected-row count, flushes pending JPA changes, and clears the persistence context. The service reloads the adjustment before mapping its DTO, so the response does not use stale managed state. Unknown IDs return `adjustment_missing`. Hidden products do not block historical edits. Quantity, stock, timestamp, request ID, and original fingerprint remain unchanged.

[`StockHistoryQuery`](../backend/src/main/java/com/stockroom/erp/stock/StockHistoryQuery.java) uses a parameterized native `UNION ALL` through `JdbcTemplate` on the same datasource and read-only service transaction. A DTO projection suits rows from two independent business tables without adding a synthetic entity. Adjustments use the current referenced product name, including hidden products. Sale rows use saved item names, negative quantities, and internal reason `Sale`. Ordering is createdAt descending, source under C collation, then UUID. The limit defaults to 50 and is validated from 1 through 1000. The query performs no SQL writes and needs no persistence-context refresh. [`HistoryEntryResponse`](../backend/src/main/java/com/stockroom/erp/stock/HistoryEntryResponse.java) maps scalar JDBC values directly to the contract. Sale-derived history rows remain read-only in the app. Sale writes and sales-list reads belong to step 5.

### App requests, recovery, and screen behavior

[`repositories/stock.ts`](../app/src/repositories/stock.ts) validates adjustment/history DTOs, signed integer bounds, sources, UUIDs, and timestamps. It sends explicit adjustment and reason-only PATCH bodies. [`api/client.ts`](../app/src/api/client.ts) now accepts an explicit backend for recovery GETs. It still makes one HTTP attempt and never replays a mutation. UUID generation was copied into `api/ids.ts` so the new API path does not depend on offline record helpers. The current stock history type lives in `types.ts`; isolated legacy database types remain for step 7 cleanup.

[`api/requestRecovery.ts`](../app/src/api/requestRecovery.ts) uses AsyncStorage 2.2.0 only for `{requestId, operationType, apiBaseUrl, submittedAt}` markers. Serialized read/modify/write operations preserve every outstanding marker across concurrent local access. Malformed storage fails closed instead of overwriting reminders. Marker persistence completes before any adjustment POST. Persistence failure prevents submission. Network errors, timeouts, malformed success responses, uncertain server failures, and lookup 404 retain markers. Structured definitive rejections after rollback permit removal. A confirmed response remains successful if later marker cleanup fails; the retained reminder can be checked again.

[`useAppState`](../app/src/app/useAppState.ts) loads markers at startup and offers explicit lookup against each recorded backend. It never silently switches recovery to the configured server and never resends a stored request. Confirmation displays the saved adjustment and refreshes current-backend lists. A lookup miss remains unresolved. Manual reconciliation requires an explicit confirmation explaining that dismissal does not cancel a server request. New adjustment actions check stored markers again and remain blocked until outstanding requests are confirmed or reconciled. This version offers lookup/reconciliation rather than an in-memory mutation retry. No request body, product row, cart, queue, or business data is persisted. Future checkout markers are preserved but their lookup remains unavailable until step 5.

The existing stock modals and history cards now call the API. Synchronous guards and saving states prevent repeated submissions, editing, and dismissal while saving. Failed requests keep entered values. An unchanged translated automatic reason maps back to `sale-shortage-replenishment` before PATCH. Cart shortage replenishment uses the same guarded adjustment flow and internal reason; it remains saved independently of any future checkout. Checkout remains disabled. History loads independently of catalog startup and has its own error/retry action. Failed reads preserve fetched rows. Revision guards stop older reads from overwriting confirmed edits, and post-write refresh failures report the confirmed save separately. Portuguese and English translations cover the new states and recovery actions.

Older installed builds can still open the catalog because marker storage loads on demand; missing native storage produces a translated storage error and blocks adjustment POSTs. ### Product mappings, queries, DTOs, and transactions

[`Product`](../backend/src/main/java/com/stockroom/erp/product/Product.java) keeps the existing UUID, integer-cent, signed-stock, and UTC timestamp mappings from V1. `updateMetadata` assigns only name, barcode, category, cost, selling price, and updatedAt. [`ProductRepository`](../backend/src/main/java/com/stockroom/erp/product/ProductRepository.java) still extends `JpaRepository`. `saveAndFlush` handles creation; managed entity dirty checking handles metadata updates and deletion. The derived `findByBarcodeAndDeletedAtIsNull` query finds an exact active barcode. `findActiveOrdered` is a native read query because PostgreSQL `translate` and C collation must match the contract's ASCII-only name ordering. It filters hidden products and orders by createdAt descending, folded name, then UUID. Ordinary writes remain JPA operations. No duplicate-name precheck uses a broader case-folding rule.

[`ProductService`](../backend/src/main/java/com/stockroom/erp/product/ProductService.java) owns the transaction boundary. Creation trims strings and defaults blank categories, empty barcodes, and omitted opening stock. Update and deletion first call `findByIdForUpdate`, including hidden rows, under READ COMMITTED with a 20-second transaction limit. They do not first load an unlocked product or merge a request-built entity. Updates reject hidden products; repeated deletion returns 204 without changing its timestamp. The configured 5-second PostgreSQL lock timeout returns `503 inventory_busy` after rollback.

[`CreateProductRequest`](../backend/src/main/java/com/stockroom/erp/product/CreateProductRequest.java) and [`UpdateProductRequest`](../backend/src/main/java/com/stockroom/erp/product/UpdateProductRequest.java) are explicit input DTOs. Field binding distinguishes omitted optional fields from forbidden explicit null values. Only cost accepts null. Bean Validation rejects missing/blank names and negative or unsafe money. [`JsonConfiguration`](../backend/src/main/java/com/stockroom/erp/common/JsonConfiguration.java) rejects numeric strings, fractional integer values, scalar-to-text coercion, and repeated JSON fields. The update DTO has no stock property, so a stock field is an unknown-field validation error.

[`ProductResponse.from`](../backend/src/main/java/com/stockroom/erp/product/ProductResponse.java) maps entities inside the service transaction while Open Session in View remains disabled. Controllers return response DTOs, never entities, deletedAt, or a version. [`ApiExceptionHandler`](../backend/src/main/java/com/stockroom/erp/common/ApiExceptionHandler.java) runs outside the failed service transaction and translates the named PostgreSQL indexes to `409 product_name_taken` and `409 barcode_taken`. Unexpected constraints remain internal errors. SQL and exception messages never enter the response body.

### How the Java code maps to PostgreSQL

`Product` maps a Java UUID to `products.id`, nullable `Long costCents` to `cost_cents`, primitive `long sellingPriceCents` to `selling_price_cents`, and `int stock` to the signed integer balance. Explicit column names keep Java names independent of the schema. `GenerationType.UUID` generates business IDs on the server. UTC `Instant` values map to PostgreSQL timestamptz. Opening stock lives on the product and creates no adjustment.

`Sale` stores its canonical payment string through `PaymentMethodConverter`, never an enum ordinal. It stores cash received only for cash, alongside request identity and the original fingerprint. `SaleItem` has simple lazy references to the sale and product plus independent name/price/line-total snapshots. There is no cascading delete or bidirectional collection. `StockAdjustment` stores signed quantity, nullable reason, and its own request identity. PostgreSQL constraints protect money bounds, payment rules, positive item quantities, nonzero adjustments, and historical foreign keys.

`JpaRepository` supplies ordinary persistence. `ProductRepository.findByIdForUpdate` is the shared write-lock query, deliberately including hidden rows. Future service transactions must acquire it before using mutable product state. Request-ID lookups are derived repository methods. `SaleItemRepository` loads items for a set of sales in one query. `StockAdjustmentRepository.updateReason` uses focused JPQL referring to entity properties and changes only reason; automatic flush/clear avoids stale managed state after this bulk update.

Flyway's `V1__business_schema.sql` owns constraints and indexes. ASCII folding uses `translate` under C collation; names and nonempty barcodes remain reserved after deletion. Hibernate validates mappings after Flyway runs. SQL initialization and Open Session in View are disabled. Hikari connections set 5-second lock waits and 15-second statement limits, and service transactions default to 20 seconds. READ COMMITTED is PostgreSQL's default.

`RequestFingerprints` implements the contract's normalized compact JSON and SHA-256 hash. Checkout normalization merges duplicate quantities with overflow checks, sorts canonical UUID strings, and normalizes override sets. Unit tests use independently calculated expected hashes. The helper does not execute a mutation or provide idempotency by itself; transaction services must still implement the contract's lock/recheck and unique-constraint race handling.
