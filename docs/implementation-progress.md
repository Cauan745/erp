### Independent reads and foreground refresh

[`useOnlineList`](../app/src/app/useOnlineList.ts) owns a separate in-memory array, initial loading flag, subsequent refresh flag, error, revision, and pending promise for each list. Concurrent calls share one read. A successful write invalidates any earlier read before updating the local display or fetching again. Both rows and errors from an invalidated read are ignored. Failed current reads retain the previous array and expose a translated error. `refreshFresh` waits for an existing read to finish before starting a read that includes the confirmed write or foreground transition. It never submits a mutation.

[`useAppState`](../app/src/app/useAppState.ts) starts catalog, sales, history, and recovery-marker reads independently. [`AppContent`](../app/src/app/AppContent.tsx) keeps navigation and recovery reminders accessible even when the initial catalog request is still pending or fails. It no longer gates the whole app on the catalog. [`ListStatus`](../app/src/components/common/ListStatus.tsx) displays initial loading, refreshing, error, and explicit refresh/retry controls inside each existing list area. The sell and product tabs share catalog state; sales and inventory history keep their own state. Empty-list claims are withheld while the initial read is pending or has failed. Existing rows remain visible during refresh and after errors. The header refresh requests every list and reloads markers; its busy indicator reflects list reads only.

An `AppState` listener refreshes all lists and markers when the app returns from a nonactive state to `active`. An existing list read finishes before its foreground fetch begins, with no overlapping HTTP reads for that list. Repeated `active` notifications do not trigger additional reads. Effect cleanup removes the listener. No interval, periodic worker, background mutation, synchronization, or automatic recovery lookup was added. The header's online label describes the app's operating mode. No successful read, mutation, or historical lookup sets a connected-status badge.

Confirmed-write refreshes now follow the data they affect:

| Confirmed action | Lists refreshed |
| --- | --- |
| Product creation or soft deletion | Catalog |
| Product metadata edit | Catalog and inventory history, since adjustment names use current product metadata |
| Stock adjustment | Catalog and inventory history |
| Adjustment reason edit | Inventory history only |
| Checkout | Catalog, sales, and inventory history |
| Recovery confirmation on the configured backend | Lists affected by that operation |
| Recovery confirmation on a different recorded backend | No current-backend list changes |

Product and sale responses still update their in-memory display immediately. A failed following refresh displays the confirmed-write message separately and retains the available data. Stock adjustment responses contain no authoritative product balance, so a failed catalog refresh retains the previous balance with its refresh error rather than inventing a balance. The saved adjustment remains confirmed. Reason updates change the displayed reason immediately before refreshing history.

### Checkout queries, locks, and atomic writes

[`SaleTransactions.checkout`](../backend/src/main/java/com/stockroom/erp/sale/SaleTransactions.java) is a public Spring transaction with READ COMMITTED isolation and a 20-second bound. It first queries `SaleRepository.findByRequestId`. For a new request it acquires the shared `ProductRepository.findByIdForUpdate` pessimistic write lock one product at a time, in canonical UUID string order. It repeats the request query after the locks, before checking missing/hidden products, current prices, or stock. A matching duplicate returns its committed response even if the original sale exhausted stock or the product has since been hidden. A different fingerprint returns `request_id_reused`.

The transaction computes each line and the total from locked active products using checked multiplication/addition and safe-integer limits. It returns `total_changed` with authoritative item prices and totals before writing if the submitted total differs. Shortages include every unapproved insufficient product in canonical order. Only IDs explicitly included in the submitted override set can go negative. Cash must cover the authoritative total; noncash stores null. Stock subtraction must remain within signed 32-bit bounds even when an override is approved.

After validation, managed products receive their stock decrements, `SaleRepository.saveAndFlush` inserts the sale, and `SaleItemRepository.saveAllAndFlush` inserts the ordered snapshots. These writes and all stock changes share one datasource and transaction. Any insert, constraint, or arithmetic failure rolls everything back. DTO mapping happens before leaving that transaction, and the controller returns success only after the proxy commits. No network call or user prompt runs while these locks are held. Existing PostgreSQL lock and statement timeouts remain five and fifteen seconds; bounded contention maps to `inventory_busy` after rollback.

[`SaleService.checkout`](../backend/src/main/java/com/stockroom/erp/sale/SaleService.java) catches only `sales_request_id_unique` outside the failed transaction. The loser has fully rolled back before `SaleTransactions.winner` opens a fresh read transaction and compares the committed winner's fingerprint. This handles same-ID races involving different product sets, which product locks alone cannot serialize. Other constraints remain ordinary server errors. No generic operation table, repository wrapper, or service interface was added.

### How the Java code maps to PostgreSQL

`Product` maps a Java UUID to `products.id`, nullable `Long costCents` to `cost_cents`, primitive `long sellingPriceCents` to `selling_price_cents`, and `int stock` to the signed integer balance. Explicit column names keep Java names independent of the schema. `GenerationType.UUID` generates business IDs on the server. UTC `Instant` values map to PostgreSQL timestamptz. Opening stock lives on the product and creates no adjustment.

`Sale` stores its canonical payment string through `PaymentMethodConverter`, never an enum ordinal. It stores cash received only for cash, alongside request identity and the original fingerprint. `SaleItem` has simple lazy references to the sale and product plus independent name/price/line-total snapshots. There is no cascading delete or bidirectional collection. `StockAdjustment` stores signed quantity, nullable reason, and its own request identity. PostgreSQL constraints protect money bounds, payment rules, positive item quantities, nonzero adjustments, and historical foreign keys.

`JpaRepository` supplies ordinary persistence. `ProductRepository.findByIdForUpdate` is the shared write-lock query, deliberately including hidden rows. Future service transactions must acquire it before using mutable product state. Request-ID lookups are derived repository methods. `SaleItemRepository` loads items for a set of sales in one query. `StockAdjustmentRepository.updateReason` uses focused JPQL referring to entity properties and changes only reason; automatic flush/clear avoids stale managed state after this bulk update.

Flyway's `V1__business_schema.sql` owns constraints and indexes. ASCII folding uses `translate` under C collation; names and nonempty barcodes remain reserved after deletion. Hibernate validates mappings after Flyway runs. SQL initialization and Open Session in View are disabled. Hikari connections set 5-second lock waits and 15-second statement limits, and service transactions default to 20 seconds. READ COMMITTED is PostgreSQL's default.

`RequestFingerprints` implements the contract's normalized compact JSON and SHA-256 hash. Checkout normalization merges duplicate quantities with overflow checks, sorts canonical UUID strings, and normalizes override sets. Unit tests use independently calculated expected hashes. The helper does not execute a mutation or provide idempotency by itself; transaction services must still implement the contract's lock/recheck and unique-constraint race handling.
